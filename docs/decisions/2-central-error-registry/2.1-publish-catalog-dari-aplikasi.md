# 2.1 Publish Catalog dari Aplikasi

[← Kembali ke 2. Central Error Registry](./README.md)

> **TL;DR:** setiap kali aplikasi di-build, daftar error lengkapnya dikirim ke registry pusat, tetapi aplikasi tetap bisa di-deploy dan berjalan walaupun registry sedang tidak bisa dihubungi.

## Tujuan

Menetapkan cara aplikasi mengirim catalog ke Central Error Registry: identitas aplikasi, isi kiriman, transport, autentikasi, dan perilaku ketika publish gagal.

## Keputusan

### Batas Package dan Registry

Package hanya menyediakan sisi pengirim. Central Error Registry merupakan aplikasi terpisah yang menerima catalog dari banyak aplikasi. Dokumen ini menetapkan kontrak di antara keduanya sehingga server registry dapat dibangun tanpa bergantung pada detail internal package.

### Command

Publish dilakukan melalui Artisan command:

```shell
php artisan error-definition:publish --revision=<commit-sha>
```

Command menyusun catalog di memory melalui shared pipeline [Decision 1.10](../1-error-definition-framework/1.10-generator-error-codes-typescript.md), termasuk discovery dan pemeriksaan EDF linter, lalu mengirimkannya. Command tidak membaca file `catalog_path` dan tidak menulis file apa pun.

Option `--revision` wajib diisi dengan identitas source revision yang sedang di-build, umumnya commit SHA dari CI.

### Identitas Aplikasi

Setiap aplikasi memiliki identitas tetap pada config `registry.application`. Nilainya berupa slug huruf kecil:

```regex
^[a-z0-9]+(?:-[a-z0-9]+)*$
```

Contoh: `surat-masuk`, `kepegawaian`.

Identitas aplikasi tidak diambil dari `APP_NAME`. Command gagal sebelum mengirim apa pun jika `registry.application` kosong atau tidak sesuai format.

### Isi Kiriman

Request body membungkus catalog [Decision 1.11](../1-error-definition-framework/1.11-generator-error-catalog-json.md) tanpa mengubah isinya:

```json
{
  "application": "surat-masuk",
  "revision": "a1b2c3d4e5f6",
  "catalog": {
    "schemaVersion": 1,
    "errors": [
      {
        "code": "SM-WF-001",
        "message": "Draft sedang dikunci.",
        "category": "workflow",
        "httpStatus": 409,
        "severity": "medium",
        "retryable": false
      }
    ]
  }
}
```

Setiap publish mengirim catalog lengkap aplikasi, bukan hanya perubahan. Error code yang tidak lagi ada pada catalog berarti sudah dihapus dari aplikasi pada revision tersebut.

Publish ulang dengan application, revision, dan catalog yang sama bersifat idempotent dan tidak dicatat sebagai perubahan baru.

### Transport dan Autentikasi

Command mengirim `POST {registry.url}/api/catalogs` melalui HTTPS dengan `Content-Type: application/json`.

Autentikasi menggunakan bearer token dari `registry.token`. Satu token hanya berlaku untuk satu identitas aplikasi. Registry menolak kiriman yang `application`-nya tidak sesuai dengan token.

Token dan URL dibaca dari environment variable melalui config, tidak ditulis langsung pada file config yang di-commit.

### Respons Registry

| Status | Arti | Exit code command |
|--------|------|-------------------|
| `2xx` | Catalog diterima atau tidak berubah. | `0` |
| `401` / `403` | Token tidak valid atau tidak berhak atas aplikasi tersebut. | `1` |
| `422` | Catalog ditolak, misalnya schema tidak valid atau error code bentrok dengan aplikasi lain. | `1` |
| Lainnya, timeout, atau network error | Registry tidak dapat memproses kiriman. | `1` |

Respons `422` membawa daftar alasan penolakan yang ditampilkan command. Bentuk detail alasan ditetapkan bersama keputusan validasi schema dan duplicate detection.

Command menunggu respons paling lama `registry.timeout` detik dan tidak melakukan retry otomatis.

### Posisi pada CI

Publish dijalankan sebagai langkah CI yang terpisah dari deployment. Kegagalan publish membuat langkah tersebut gagal, tetapi tidak menghentikan atau membatalkan deployment.

## Alasan

Menyusun catalog di memory memastikan yang dikirim selalu sesuai dengan source yang sedang di-build. Membaca file `catalog_path` berisiko mengirim artifact lama dari build sebelumnya.

Identitas aplikasi dipisahkan dari `APP_NAME` karena `APP_NAME` adalah nama tampilan yang dapat berubah. Registry memerlukan key yang stabil untuk menghubungkan riwayat error satu aplikasi.

Revision diwajibkan agar registry dapat mencatat kapan sebuah error code muncul, berubah, atau hilang. Tanpa revision, riwayat hanya berbasis waktu publish dan sulit dicocokkan dengan kode.

Catalog lengkap dipilih dibanding kiriman perubahan karena registry dapat menghitung perbedaan sendiri, dan kiriman yang hilang tidak membuat data registry menyimpang dari aplikasi. Kiriman berikutnya selalu memperbaiki keadaan.

Envelope dipisahkan dari catalog agar `schemaVersion` dan isi catalog tetap identik dengan artifact Decision 1.11, sedangkan identitas aplikasi dan revision menjadi urusan publish.

Token per aplikasi membatasi dampak kebocoran: token satu aplikasi tidak dapat menimpa catalog aplikasi lain.

Retry otomatis tidak disediakan karena CI sudah memiliki mekanisme menjalankan ulang langkah yang gagal. Retry di dalam command hanya memperlama build ketika registry memang sedang tidak tersedia.

Deployment tidak bergantung pada publish sesuai [Decision 1.1.1](../1-error-definition-framework/1.1.1-batas-metadata-runtime-dan-registry.md): registry adalah consumer, bukan dependency aplikasi.

✅ **Contoh:** Registry sedang maintenance ketika aplikasi di-deploy → deployment tetap berjalan, langkah publish gagal, lalu dijalankan ulang setelah registry kembali, karena catalog selalu dikirim lengkap dan tidak ada data yang hilang.

❌ **Bukan contoh:** Registry menolak catalog dengan `422` karena `SM-WF-001` sudah dipakai aplikasi lain → menjalankan ulang langkah publish tidak menyelesaikan masalah, karena yang harus diperbaiki adalah error code di source aplikasi.

## Keputusan Terkait

- Registry sebagai consumer ditetapkan pada [Decision 1.1.1](../1-error-definition-framework/1.1.1-batas-metadata-runtime-dan-registry.md).
- Shared generation pipeline ditetapkan pada [Decision 1.10](../1-error-definition-framework/1.10-generator-error-codes-typescript.md).
- Bentuk catalog ditetapkan pada [Decision 1.11](../1-error-definition-framework/1.11-generator-error-catalog-json.md).
- Config key tercatat pada [Configuration Reference](../../reference/configuration.md).

## Konsekuensi

- Setiap aplikasi wajib memiliki `registry.application` yang stabil sebelum dapat publish.
- Mengganti identitas aplikasi dianggap sebagai aplikasi baru oleh registry.
- CI harus menyediakan commit SHA dan menyimpan token registry sebagai secret.
- Server registry wajib menerima envelope dan endpoint yang ditetapkan di sini.
- Penghapusan error code terdeteksi dari catalog lengkap, tanpa perintah hapus terpisah.
- Data registry dapat tertinggal dari aplikasi selama publish gagal dan belum dijalankan ulang.
- Package tidak menyediakan server registry.
