# 2.2 Validasi Schema

[← Kembali ke 2. Central Error Registry](./README.md)

> **TL;DR:** registry memeriksa setiap daftar error yang masuk dengan aturan yang sama seperti di aplikasi, lalu menolak seluruh kiriman beserta alasan yang jelas jika ada satu bagian yang salah.

## Tujuan

Menetapkan apa yang diperiksa registry pada setiap kiriman publish, bagaimana aturan tersebut dijaga tetap sama dengan aplikasi, dan bentuk penolakan yang dikembalikan.

## Keputusan

### Sumber Aturan

Aturan struktur kiriman ditetapkan dalam JSON Schema yang disertakan package:

- `resources/schemas/publish-request.v1.json` untuk envelope [Decision 2.1](./2.1-publish-catalog-dari-aplikasi.md);
- `resources/schemas/error-catalog.v1.json` untuk catalog `schemaVersion: 1` pada [Decision 1.11](../1-error-definition-framework/1.11-generator-error-catalog-json.md).

Registry memvalidasi kiriman dengan file schema yang sama. Setiap `schemaVersion` baru mendapat file schema baru tanpa mengubah file versi sebelumnya.

### Yang Diperiksa

Envelope:

- `application` sesuai format slug Decision 2.1;
- `revision` berupa string tidak kosong dengan panjang maksimal 64 karakter;
- `catalog` berupa object.

Catalog:

- `schemaVersion` didukung oleh registry;
- `errors` berupa array;
- setiap error memiliki seluruh field runtime dengan tipe yang benar;
- `code` mengikuti format `^[A-Z0-9]+(?:-[A-Z0-9]+)+-\d{3,}$`;
- `message` tidak kosong setelah whitespace dihapus;
- `category` dan `severity` merupakan backing value enum yang dikenal;
- `httpStatus` berada pada rentang `400–599`;
- `retryable` berupa boolean;
- setiap `code` hanya muncul satu kali dalam catalog.

Field yang tidak dikenal pada envelope maupun catalog diabaikan dan tidak disimpan.

Catalog dengan `errors` kosong diterima dan berarti aplikasi sudah tidak memiliki Error Definition.

### Penolakan

Validasi bersifat menyeluruh: seluruh pelanggaran dikumpulkan, lalu kiriman ditolak secara utuh. Registry tidak menyimpan sebagian catalog.

Penolakan menggunakan HTTP `422` dengan bentuk:

```json
{
  "message": "Catalog ditolak.",
  "findings": [
    {
      "ruleId": "REG005",
      "path": "catalog.errors[3].code",
      "message": "Error code 'SM-01' tidak mengikuti format."
    }
  ]
}
```

`path` menunjuk lokasi pelanggaran dalam request body. Command publish menampilkan setiap finding dengan rule ID, path, dan message.

### Rule ID

| Rule ID | Kondisi |
|---------|---------|
| `REG001` | Request body bukan JSON object yang valid. |
| `REG002` | `application` tidak valid. |
| `REG003` | `revision` tidak valid. |
| `REG004` | `schemaVersion` tidak didukung. |
| `REG005` | Error code tidak mengikuti format. |
| `REG006` | Field error hilang, bertipe salah, atau bernilai di luar pilihan yang dikenal. |
| `REG007` | Message kosong. |
| `REG008` | HTTP status di luar rentang `400–599`. |
| `REG009` | Error code muncul lebih dari satu kali dalam catalog. |

Rule ID bersifat stabil. Rule yang dihapus tidak dipakai ulang untuk kondisi lain.

## Alasan

JSON Schema dipilih karena merupakan standar yang dapat dibaca oleh server registry dalam bahasa apa pun. Menyertakannya di package membuat aturan registry dan aplikasi berasal dari satu sumber, sehingga catalog yang lolos linter tidak ditolak karena perbedaan aturan.

Registry tetap memvalidasi walaupun aplikasi sudah menjalankan linter, karena registry tidak dapat memastikan pengirim memakai versi package yang benar atau tidak mengubah catalog secara manual.

Field tidak dikenal diabaikan agar package versi baru yang menambahkan field secara non-breaking tetap dapat publish ke registry lama. Perubahan yang breaking tetap ditandai dengan `schemaVersion` baru sesuai Decision 1.11.

Penolakan utuh dipilih karena catalog sebagian membuat registry menganggap error code yang ditolak sudah dihapus dari aplikasi, sesuai aturan catalog lengkap pada Decision 2.1.

Seluruh pelanggaran dikumpulkan sekaligus agar developer dapat memperbaiki semua masalah dalam satu kali perubahan, konsisten dengan perilaku linter pada [Decision 1.8](../1-error-definition-framework/1.8-validator-dan-linter.md).

Rule ID menggunakan prefix `REG` agar temuan registry dapat dibedakan dari temuan linter lokal (`EDF`, `VAL`) di log CI.

✅ **Contoh:** Package versi baru menambahkan field opsional `docsUrl` pada setiap error tanpa mengubah `schemaVersion` → registry lama tetap menerima catalog dan mengabaikan field tersebut, karena perubahan non-breaking tidak boleh memutus publish.

❌ **Bukan contoh:** Package mengubah `httpStatus` dari integer menjadi string → ini breaking change yang wajib menaikkan `schemaVersion`, karena registry lama akan salah membaca field yang sudah dikenalnya.

## Keputusan Terkait

- Envelope publish ditetapkan pada [Decision 2.1](./2.1-publish-catalog-dari-aplikasi.md).
- Bentuk catalog ditetapkan pada [Decision 1.11](../1-error-definition-framework/1.11-generator-error-catalog-json.md).
- Rule Error Definition aplikasi ditetapkan pada [Decision 1.8](../1-error-definition-framework/1.8-validator-dan-linter.md).
- Error code yang bentrok antar-aplikasi ditetapkan pada [Decision 2.3](./2.3-deteksi-error-code-duplikat.md).

## Konsekuensi

- Package wajib menyertakan dan menjaga file JSON Schema untuk setiap `schemaVersion`.
- Perubahan aturan format error code harus dilakukan bersamaan di linter dan JSON Schema.
- Satu error code yang salah membuat seluruh catalog aplikasi tidak tercatat sampai diperbaiki.
- Registry dapat mendukung beberapa `schemaVersion` sekaligus selama masa transisi.
- Field tambahan dari package versi baru tidak tersedia di registry sampai registry diperbarui.
