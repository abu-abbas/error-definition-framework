# 2.3 Deteksi Error Code Duplikat

[← Kembali ke 2. Central Error Registry](./README.md)

> **TL;DR:** satu kode error hanya boleh dimiliki satu aplikasi untuk selamanya, sehingga kode yang dilihat pengguna atau tim support selalu menunjuk ke satu tempat yang jelas.

## Tujuan

Menetapkan kepemilikan error code di seluruh aplikasi yang terdaftar pada registry, cara menangani kode yang bentrok, dan nasib kode yang sudah dihapus.

## Keputusan

### Kepemilikan Error Code

Error code unik secara global di registry, bukan hanya di dalam satu aplikasi.

Aplikasi yang pertama kali berhasil publish sebuah error code menjadi pemilik kode tersebut. Publish berikutnya dari aplikasi yang sama boleh mengubah message, category, HTTP status, severity, dan retryable kode tersebut.

### Kode yang Bentrok

Kiriman yang memuat error code milik aplikasi lain ditolak secara utuh dengan HTTP `422` dan rule berikut, menggunakan bentuk penolakan [Decision 2.2](./2.2-validasi-schema.md):

| Rule ID | Kondisi |
|---------|---------|
| `REG010` | Error code sudah dimiliki aplikasi lain. |

Message finding menyebut aplikasi pemilik kode tersebut.

Pemeriksaan berlaku untuk seluruh kode dalam kiriman. Kode yang bentrok tidak dilewati sambil menerima kode lainnya.

### Kode yang Dihapus

Error code yang tidak lagi ada pada catalog aplikasi pemiliknya ditandai sebagai dihapus, tetapi tetap menjadi milik aplikasi tersebut.

Aplikasi lain tidak dapat memakai kode yang sudah dihapus. Aplikasi pemilik dapat memakainya kembali, dan kode tersebut kembali berstatus aktif.

### Pemindahan Kepemilikan

Kepemilikan tidak berpindah secara otomatis. Pemindahan kode ke aplikasi lain, misalnya karena modul dipindahkan, dilakukan sebagai tindakan administratif di registry sebelum aplikasi tujuan publish.

### Konvensi Prefix

Registry tidak memesan prefix. Untuk mengurangi bentrok, segmen pertama error code sebaiknya menandai aplikasi atau domain yang spesifik, bukan konsep umum yang ada di banyak aplikasi.

## Alasan

Error code dipakai sebagai key oleh pengguna, log, monitoring, dan tim support. Jika satu kode dapat berarti dua hal berbeda di dua aplikasi, pencarian di registry tidak lagi dapat memberikan satu jawaban yang pasti.

Prinsip pemilik pertama dipilih karena tidak memerlukan pendaftaran manual sebelum aplikasi dapat publish. Alternatif pendaftaran kode atau prefix terlebih dahulu ditolak karena menambah langkah administratif untuk setiap error baru.

Kode yang dihapus tetap dimiliki karena log, tiket support, dan aplikasi client versi lama masih dapat menyebutnya. Memberikannya ke aplikasi lain membuat catatan lama menunjuk ke arti yang salah.

Pemindahan dibuat eksplisit agar perpindahan kode antar-aplikasi selalu merupakan keputusan yang disengaja, bukan efek samping dari urutan deployment.

Pemesanan prefix tidak dilakukan karena satu aplikasi umumnya memiliki banyak prefix modul dan struktur prefix tidak ditetapkan oleh framework. Keunikan pada level kode sudah cukup untuk mencegah arti ganda.

✅ **Contoh:** Aplikasi `surat-masuk` memakai `SM-WF-001`, lalu aplikasi `kepegawaian` mencoba publish `SM-WF-001` → publish `kepegawaian` ditolak dengan `REG010`, karena kode yang sama tidak boleh memiliki dua arti.

❌ **Bukan contoh:** Aplikasi `surat-masuk` menghapus `SM-WF-001`, lalu menambahkannya kembali beberapa revision kemudian → diterima dan kode kembali aktif, karena pemiliknya tetap aplikasi yang sama.

✅ **Contoh:** Dua aplikasi sama-sama memiliki modul user dan memakai prefix `USER` → aplikasi kedua kemungkinan besar bentrok, sehingga prefix sebaiknya spesifik, misalnya `KPG-USER-001` untuk aplikasi kepegawaian.

## Keputusan Terkait

- Catalog lengkap dan penghapusan kode ditetapkan pada [Decision 2.1](./2.1-publish-catalog-dari-aplikasi.md).
- Bentuk penolakan dan rule ID ditetapkan pada [Decision 2.2](./2.2-validasi-schema.md).
- Keunikan error code di dalam satu aplikasi diperiksa linter pada [Decision 1.8](../1-error-definition-framework/1.8-validator-dan-linter.md).
- Error code sebagai key penghubung ditetapkan pada [Decision 1.1.1](../1-error-definition-framework/1.1.1-batas-metadata-runtime-dan-registry.md).

## Konsekuensi

- Setiap error code di registry selalu menunjuk ke tepat satu aplikasi.
- Urutan publish pertama menentukan pemilik ketika dua aplikasi menambahkan kode yang sama secara bersamaan.
- Jumlah kode yang tercatat terus bertambah karena kode yang dihapus tidak pernah dilepas.
- Aplikasi yang ditolak `REG010` harus mengganti error code di source, bukan mengulang publish.
- Registry memerlukan fitur administratif untuk memindahkan kepemilikan kode.
- Bentrok antar-aplikasi baru terdeteksi saat publish, bukan saat linter lokal berjalan.
