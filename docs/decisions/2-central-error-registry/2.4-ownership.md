# 2.4 Ownership

[← Kembali ke 2. Central Error Registry](./README.md)

> **TL;DR:** setiap kode error punya tim penanggung jawab dan panduan penanganan yang dicatat di registry, sehingga tim support tahu harus berbuat apa dan menghubungi siapa tanpa menunggu developer.

## Tujuan

Menetapkan informasi organisasi yang dicatat registry untuk setiap error code, siapa yang mengelolanya, dan bagaimana informasi tersebut tetap relevan ketika definisi error di aplikasi berubah.

## Keputusan

### Tim sebagai Pemilik

Penanggung jawab dicatat sebagai tim, bukan individu. Setiap tim memiliki nama dan kanal kontak.

Setiap aplikasi memiliki satu tim pemilik. Seluruh error code aplikasi tersebut mengikuti tim pemilik aplikasi, kecuali error code tertentu diberi tim lain secara eksplisit.

### Enrichment per Error Code

Registry dapat mencatat informasi berikut untuk setiap error code:

- tim penanggung jawab jika berbeda dari tim pemilik aplikasi;
- panduan penanganan untuk support;
- link artikel Knowledge Base;
- tim eskalasi.

Seluruh field enrichment bersifat opsional.

SLA tidak dicatat per error code. SLA ditetapkan pada tim berdasarkan severity, sehingga target waktu sebuah error berasal dari tim penanggung jawab dan severity pada catalog.

### Pengelolaan

Enrichment dikelola langsung di registry oleh tim terkait. Enrichment tidak dikirim melalui publish dan tidak ditulis di source aplikasi, sesuai [Decision 1.1.1](../1-error-definition-framework/1.1.1-batas-metadata-runtime-dan-registry.md).

Enrichment terikat pada error code. Perubahan message pada catalog tidak menghapus enrichment.

### Perlu Ditinjau

Ketika publish mengubah `category`, `httpStatus`, `severity`, atau `retryable` sebuah error code, registry menandai enrichment kode tersebut sebagai perlu ditinjau. Tanda dihapus setelah tim penanggung jawab mengonfirmasi atau memperbarui enrichment.

Perubahan `message` saja tidak memicu tanda perlu ditinjau.

### Aplikasi Tanpa Pemilik

Publish dari aplikasi yang belum memiliki tim pemilik tetap diterima. Registry menampilkan aplikasi dan error code tersebut sebagai belum memiliki pemilik.

## Alasan

Tim dipilih sebagai pemilik karena individu dapat berpindah atau keluar. Kepemilikan per individu membuat banyak error code kehilangan penanggung jawab setiap kali terjadi perubahan organisasi.

Kepemilikan per aplikasi dengan pengecualian per kode mengurangi pekerjaan administratif. Sebagian besar error code mengikuti tim aplikasinya, dan hanya modul yang dikelola tim lain perlu ditandai.

SLA diletakkan pada tim dan severity karena target waktu biasanya merupakan kebijakan tim, bukan sifat satu error. Menyimpan SLA per kode membuat ratusan nilai harus diperbarui ketika kebijakan tim berubah.

Enrichment dikelola di registry karena isinya berubah mengikuti organisasi dan proses support, bukan mengikuti deployment aplikasi.

Perubahan category, status, severity, atau retryable dapat mengubah cara error ditangani, sehingga panduan lama berisiko menyesatkan. Perubahan message umumnya hanya perbaikan kalimat dan tidak mengubah penanganan.

Publish tidak ditolak karena belum ada pemilik agar data organisasi tidak menghambat CI aplikasi. Kekurangan tersebut cukup terlihat di registry dan dapat dilengkapi kemudian.

✅ **Contoh:** `SM-WF-001` berubah dari severity `medium` menjadi `high` → enrichment ditandai perlu ditinjau, karena tingkat dampak yang berubah dapat mengubah jalur eskalasi dan SLA.

❌ **Bukan contoh:** Message `SM-WF-001` diperbaiki dari "Draft sedang dikunci." menjadi "Draft sedang dikunci oleh pengguna lain." → enrichment tidak ditandai, karena cara penanganannya tidak berubah.

## Keputusan Terkait

- Batas metadata runtime dan registry ditetapkan pada [Decision 1.1.1](../1-error-definition-framework/1.1.1-batas-metadata-runtime-dan-registry.md).
- Kepemilikan error code oleh aplikasi ditetapkan pada [Decision 2.3](./2.3-deteksi-error-code-duplikat.md).
- Riwayat perubahan yang memicu tanda perlu ditinjau ditetapkan pada [Decision 2.5](./2.5-versioning.md).

## Konsekuensi

- Registry harus menyimpan data tim, kepemilikan aplikasi, dan enrichment per error code.
- Tim support dapat memperoleh panduan penanganan tanpa membaca source aplikasi.
- Kode baru langsung memiliki penanggung jawab melalui tim pemilik aplikasi.
- Enrichment dapat tertinggal dari perubahan aplikasi sampai tim meninjaunya.
- Mengubah SLA tim langsung berlaku untuk seluruh error code yang menjadi tanggung jawabnya.
