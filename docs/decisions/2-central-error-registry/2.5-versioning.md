# 2.5 Versioning

[← Kembali ke 2. Central Error Registry](./README.md)

> **TL;DR:** registry menyimpan setiap daftar error yang pernah dikirim, sehingga bisa dilihat kapan sebuah kode muncul, berubah, atau dihapus, dan versi aplikasi mana yang membawanya.

## Tujuan

Menetapkan apa yang disimpan registry dari setiap publish, bagaimana riwayat error code dibentuk, dan keadaan mana yang dianggap terkini.

## Keputusan

### Catalog Version

Setiap publish yang diterima dan mengubah catalog disimpan sebagai catalog version dengan:

- application;
- revision;
- waktu diterima;
- isi catalog;
- hash isi catalog.

Publish dengan isi catalog yang sama dengan catalog version terakhir aplikasi tersebut tidak membuat version baru, walaupun revision berbeda. Registry hanya mencatat bahwa revision tersebut membawa catalog yang sama.

Catalog version disimpan tanpa batas waktu.

### Keadaan Terkini

Keadaan terkini sebuah aplikasi adalah catalog version yang terakhir diterima, berdasarkan waktu diterima registry, bukan berdasarkan urutan revision.

Publish dari revision lama setelah revision baru, misalnya karena rollback deployment, menjadi keadaan terkini.

Registry menyimpan satu keadaan terkini per aplikasi. Publish dijalankan dari pipeline yang melakukan deployment ke production.

### Riwayat Error Code

Registry membentuk riwayat setiap error code dengan membandingkan catalog version yang berurutan. Setiap perubahan dicatat sebagai event:

| Event | Kondisi |
|-------|---------|
| `added` | Kode pertama kali muncul. |
| `changed` | Satu atau lebih field runtime berubah. Event mencatat field beserta nilai sebelum dan sesudah. |
| `removed` | Kode tidak lagi ada pada catalog. |
| `restored` | Kode yang sebelumnya dihapus muncul kembali. |

Setiap event mencatat application, revision, dan waktu diterima.

## Alasan

Menyimpan catalog utuh untuk setiap version membuat registry dapat menunjukkan keadaan aplikasi pada revision mana pun tanpa menyusun ulang dari event. Ukuran catalog kecil sehingga penyimpanan tanpa batas waktu tidak menjadi beban berarti.

Hash isi dipakai agar deployment yang tidak mengubah error tidak memenuhi riwayat dengan version yang identik.

Waktu diterima dipakai sebagai urutan karena commit SHA tidak dapat diurutkan. Rollback juga merupakan keadaan nyata di production, sehingga registry harus mengikutinya.

Satu keadaan per aplikasi dipilih agar tim support melihat error yang benar-benar dapat terjadi di production. Mencatat environment seperti staging menambah dimensi pada setiap pencarian dan belum dibutuhkan.

Event dibentuk dari perbandingan catalog lengkap sehingga aplikasi tidak perlu mengirim informasi perubahan secara terpisah, sesuai [Decision 2.1](./2.1-publish-catalog-dari-aplikasi.md).

✅ **Contoh:** Aplikasi deploy revision `b2`, lalu rollback ke `a1` karena bug → registry menerima publish `a1` dan menjadikannya keadaan terkini, karena itu catalog yang sedang berjalan di production.

❌ **Bukan contoh:** Branch fitur dideploy ke staging dan menjalankan publish → tidak dilakukan, karena registry hanya mencatat satu keadaan per aplikasi dan error di staging belum dapat terjadi di production.

## Konsekuensi

- Registry dapat menjawab kapan dan pada revision mana sebuah error code berubah.
- Rollback langsung tercermin pada keadaan terkini dan riwayat error code.
- Riwayat bergantung pada publish dijalankan setiap deployment production.
- Error code yang hanya ada di staging tidak tercatat di registry.
- Riwayat event dapat dibentuk ulang dari catalog version yang tersimpan.
