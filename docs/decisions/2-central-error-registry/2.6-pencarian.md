# 2.6 Pencarian

[← Kembali ke 2. Central Error Registry](./README.md)

> **TL;DR:** siapa pun di tim cukup mengetik kode error yang dilihat pengguna untuk langsung tahu artinya, aplikasinya, siapa yang menangani, dan apa yang harus dilakukan.

## Tujuan

Menetapkan cara error code dicari di registry, informasi yang ditampilkan, dan siapa yang dapat mengaksesnya.

## Keputusan

### Pencarian Kode

Pencarian utama adalah berdasarkan error code. Input dinormalisasi sebelum dicocokkan:

- huruf diubah menjadi uppercase;
- spasi, underscore, dan titik diperlakukan sebagai `-`;
- spasi di awal dan akhir dihapus.

Input `sm wf 001`, `sm_wf_001`, dan `SM-WF-001` menemukan kode yang sama.

Kode yang cocok persis selalu ditampilkan paling atas. Input yang hanya berupa bagian awal kode, misalnya `SM-WF`, menampilkan seluruh kode dengan prefix tersebut.

### Pencarian Teks dan Filter

Selain kode, pencarian dapat dilakukan pada teks message dan panduan penanganan.

Hasil dapat difilter berdasarkan:

- aplikasi;
- category;
- severity;
- tim penanggung jawab;
- status aktif atau dihapus;
- tanda perlu ditinjau.

### Hasil

Setiap hasil menampilkan:

- metadata runtime terkini: code, message, category, HTTP status, severity, retryable;
- aplikasi pemilik dan status kode;
- enrichment [Decision 2.4](./2.4-ownership.md);
- riwayat perubahan [Decision 2.5](./2.5-versioning.md).

Kode yang dihapus tetap dapat dicari dan ditampilkan dengan label dihapus, beserta revision terakhir yang memuatnya.

### Akses

Registry hanya dapat diakses pengguna internal yang login. Seluruh pengguna yang login dapat mencari dan melihat semua error code. Mengubah enrichment hanya dapat dilakukan anggota tim penanggung jawab.

### API

Pencarian yang sama tersedia sebagai API read-only untuk tooling:

```text
GET /api/errors/{code}
GET /api/errors?q={teks}&application={slug}&status={active|removed}
```

API menggunakan token baca yang terpisah dari token publish [Decision 2.1](./2.1-publish-catalog-dari-aplikasi.md).

## Alasan

Kode error adalah satu-satunya informasi yang pasti dimiliki tim support ketika pengguna melapor, sehingga pencarian kode harus menjadi jalur tercepat.

Normalisasi input dipilih karena pengguna sering menyalin atau mengetik ulang kode dari layar atau foto dengan format yang tidak persis. Format error code yang ketat pada [Decision 1.8](../1-error-definition-framework/1.8-validator-dan-linter.md) membuat normalisasi ini tidak menimbulkan arti ganda.

Kode yang dihapus tetap dapat dicari karena laporan pengguna, log, dan aplikasi client versi lama masih dapat menampilkannya.

Akses dibatasi untuk pengguna internal karena message dan panduan penanganan dapat memuat informasi proses internal. Seluruh pengguna internal dapat membaca agar tim support tidak perlu meminta akses per aplikasi.

Token baca dipisahkan dari token publish agar tooling yang hanya membaca tidak dapat mengubah catalog aplikasi.

✅ **Contoh:** Pengguna mengirim foto layar bertuliskan "sm-wf-001", lalu support mengetik `sm wf 001` → registry menampilkan `SM-WF-001`, karena input dinormalisasi sebelum dicocokkan.

❌ **Bukan contoh:** Support mengetik `SMWF001` → tidak dianggap sama dengan `SM-WF-001` dan diperlakukan sebagai pencarian teks, karena tanpa pemisah batas antar-segmen tidak dapat dipastikan.

## Keputusan Terkait

- Status kode yang dihapus ditetapkan pada [Decision 2.3](./2.3-deteksi-error-code-duplikat.md).
- Enrichment dan tim penanggung jawab ditetapkan pada [Decision 2.4](./2.4-ownership.md).
- Riwayat error code ditetapkan pada [Decision 2.5](./2.5-versioning.md).
- Format error code ditetapkan pada [Decision 1.8](../1-error-definition-framework/1.8-validator-dan-linter.md).

## Konsekuensi

- Tim support dapat menangani laporan berdasarkan kode tanpa membaca source aplikasi.
- Registry memerlukan autentikasi pengguna internal dan pengelolaan keanggotaan tim.
- Registry mengelola dua jenis token: publish per aplikasi dan baca untuk tooling.
- Hasil pencarian selalu mencerminkan keadaan terkini dari publish terakhir.
