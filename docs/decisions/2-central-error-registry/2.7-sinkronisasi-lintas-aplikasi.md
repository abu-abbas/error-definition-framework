# 2.7 Sinkronisasi Lintas Aplikasi

[← Kembali ke 2. Central Error Registry](./README.md)

> **TL;DR:** frontend atau aplikasi mobile yang memakai beberapa backend sekaligus bisa mengambil daftar kode error gabungan dari registry, tanpa menyalin definisi dari setiap aplikasi.

## Tujuan

Menetapkan cara consumer yang bergantung pada lebih dari satu aplikasi memperoleh error code seluruh aplikasi tersebut, dan batas sinkronisasi antara registry dan aplikasi.

## Keputusan

### Arah Sinkronisasi

Data error hanya mengalir dari aplikasi ke registry melalui publish [Decision 2.1](./2.1-publish-catalog-dari-aplikasi.md). Registry tidak mengirim, menimpa, atau mengubah Error Definition di aplikasi.

Aplikasi tidak membaca definisi aplikasi lain dari registry ketika berjalan. Setiap aplikasi hanya menghasilkan error miliknya sendiri.

### Export Gabungan

Registry menyediakan export gabungan untuk consumer yang membutuhkan error code dari beberapa aplikasi, misalnya frontend atau aplikasi mobile yang memanggil beberapa backend:

```text
GET /api/exports/error-codes.ts?applications=surat-masuk,kepegawaian
GET /api/exports/error-catalog.json?applications=surat-masuk,kepegawaian
```

Export diambil oleh consumer pada saat build menggunakan token baca [Decision 2.6](./2.6-pencarian.md).

### Isi Export

Export hanya memuat error code yang aktif pada keadaan terkini aplikasi yang diminta.

TypeScript export menggunakan bentuk yang sama dengan [Decision 1.10](../1-error-definition-framework/1.10-generator-error-codes-typescript.md), berisi gabungan kode seluruh aplikasi yang diminta dan diurutkan berdasarkan code.

JSON export menggunakan bentuk catalog [Decision 1.11](../1-error-definition-framework/1.11-generator-error-catalog-json.md) dengan tambahan field `application` pada setiap error:

```json
{
  "schemaVersion": 1,
  "errors": [
    {
      "code": "SM-WF-001",
      "application": "surat-masuk",
      "message": "Draft sedang dikunci.",
      "category": "workflow",
      "httpStatus": 409,
      "severity": "medium",
      "retryable": false
    }
  ]
}
```

Export tidak memuat enrichment [Decision 2.4](./2.4-ownership.md).

### Consumer Satu Aplikasi

Consumer yang hanya bergantung pada satu aplikasi tetap memakai artifact dari `error-definition:generate` aplikasi tersebut, bukan export registry.

## Alasan

Satu arah sinkronisasi menjaga aplikasi tetap menjadi source of truth sesuai [Decision 1.1.1](../1-error-definition-framework/1.1.1-batas-metadata-runtime-dan-registry.md). Jika registry dapat mengubah definisi aplikasi, perubahan error tidak lagi tercatat di source code dan review.

Export gabungan menyelesaikan kebutuhan frontend yang memanggil banyak backend tanpa membuat setiap backend menulis artifact ke banyak repository. Penggabungan aman karena error code unik secara global sesuai [Decision 2.3](./2.3-deteksi-error-code-duplikat.md).

Export diambil saat build, bukan saat runtime, agar consumer tidak bergantung pada ketersediaan registry ketika melayani pengguna.

Kode yang dihapus tidak diekspor karena consumer tidak perlu menangani kode yang tidak lagi dapat dikirim backend. Riwayatnya tetap tersedia melalui pencarian.

Bentuk export mengikuti artifact Stage 1 agar consumer yang berpindah dari artifact satu aplikasi ke export gabungan tidak perlu menulis ulang kode penanganan error.

Consumer satu aplikasi tidak diarahkan ke registry agar build tidak bertambah dependency tanpa manfaat.

✅ **Contoh:** Aplikasi mobile memanggil backend `surat-masuk` dan `kepegawaian` → build mobile mengambil `error-codes.ts` gabungan dari registry, karena error code berasal dari dua aplikasi.

❌ **Bukan contoh:** Frontend admin hanya memanggil backend `surat-masuk` → tetap memakai `error-codes.ts` hasil `error-definition:generate` milik `surat-masuk`, karena tidak ada kode dari aplikasi lain yang perlu digabung.

## Keputusan Terkait

- Publish dari aplikasi ditetapkan pada [Decision 2.1](./2.1-publish-catalog-dari-aplikasi.md).
- Keunikan error code global ditetapkan pada [Decision 2.3](./2.3-deteksi-error-code-duplikat.md).
- Token baca ditetapkan pada [Decision 2.6](./2.6-pencarian.md).
- Bentuk artifact ditetapkan pada [Decision 1.10](../1-error-definition-framework/1.10-generator-error-codes-typescript.md) dan [Decision 1.11](../1-error-definition-framework/1.11-generator-error-catalog-json.md).

## Konsekuensi

- Consumer multi-aplikasi bergantung pada registry saat build, bukan saat runtime.
- Export bisa tertinggal dari aplikasi selama publish gagal dan belum dijalankan ulang.
- Error code baru di aplikasi baru tersedia pada export setelah aplikasi tersebut publish.
- Field `application` menjadi bagian kontrak JSON export registry, bukan catalog aplikasi.
