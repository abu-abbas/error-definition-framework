# 2.8 Dashboard Registry

[← Kembali ke 2. Central Error Registry](./README.md)

> **TL;DR:** halaman utama registry menunjukkan apa yang perlu dibereskan, seperti aplikasi tanpa penanggung jawab atau panduan yang sudah usang, bukan sekadar angka statistik.

## Tujuan

Menetapkan isi halaman utama registry, tampilan per tim, dan batas informasi yang ditampilkan.

## Keputusan

### Perlu Ditindaklanjuti

Bagian teratas dashboard menampilkan daftar yang membutuhkan tindakan:

- aplikasi tanpa tim pemilik [Decision 2.4](./2.4-ownership.md);
- error code dengan tanda perlu ditinjau;
- error code severity `high` atau `critical` tanpa panduan penanganan;
- publish terakhir setiap aplikasi yang ditolak.

Setiap item menautkan ke halaman error code atau aplikasi terkait.

### Status Publish Aplikasi

Dashboard menampilkan untuk setiap aplikasi:

- revision dan waktu catalog version terakhir;
- hasil publish terakhir, diterima atau ditolak;
- finding dari publish yang ditolak.

Registry mencatat publish yang ditolak beserta application, revision, waktu, dan finding [Decision 2.2](./2.2-validasi-schema.md). Publish yang ditolak tidak menjadi catalog version.

### Perubahan Terbaru

Dashboard menampilkan event terbaru dari riwayat error code [Decision 2.5](./2.5-versioning.md): kode yang ditambahkan, diubah, dihapus, dan dipulihkan.

### Ringkasan

Dashboard menampilkan jumlah error code aktif per aplikasi, category, dan severity.

### Tampilan Tim

Setiap tim memiliki tampilan yang sama, tetapi dibatasi pada aplikasi dan error code yang menjadi tanggung jawabnya. Pengguna melihat tampilan timnya secara default dan dapat beralih ke tampilan seluruh registry.

### Batas Informasi

Dashboard tidak menampilkan berapa kali sebuah error terjadi. Registry tidak menerima log atau data kejadian dari aplikasi.

## Alasan

Daftar tindak lanjut diletakkan paling atas karena registry hanya bermanfaat jika datanya lengkap dan terkini. Angka ringkasan tidak memberi tahu siapa harus melakukan apa.

Error code severity tinggi tanpa panduan diprioritaskan karena kasus tersebut paling merugikan ketika support harus menanganinya tanpa arahan.

Publish yang ditolak dicatat karena kegagalan publish tidak menghentikan deployment sesuai [Decision 2.1](./2.1-publish-catalog-dari-aplikasi.md). Tanpa catatan di registry, aplikasi dapat berhenti tercatat tanpa ada yang menyadari.

Tampilan tim dipilih sebagai default agar setiap tim melihat pekerjaannya sendiri tanpa tenggelam dalam data aplikasi lain.

Jumlah kejadian error tidak ditampilkan karena data tersebut sudah dimiliki sistem logging dan monitoring. Menerima data kejadian akan menjadikan registry dependency runtime aplikasi, bertentangan dengan [Decision 1.1.1](../1-error-definition-framework/1.1.1-batas-metadata-runtime-dan-registry.md).

✅ **Contoh:** Publish `kepegawaian` ditolak karena `REG010` dan CI tidak memblokir deployment → dashboard menampilkan publish ditolak pada aplikasi tersebut, karena tanpa itu registry diam-diam tertinggal dari production.

❌ **Bukan contoh:** Tim ingin melihat `SM-WF-001` terjadi 500 kali hari ini → dilihat di sistem monitoring melalui field `error_code` pada log, karena registry tidak mencatat kejadian error.

## Keputusan Terkait

- Publish yang tidak memblokir deployment ditetapkan pada [Decision 2.1](./2.1-publish-catalog-dari-aplikasi.md).
- Finding penolakan ditetapkan pada [Decision 2.2](./2.2-validasi-schema.md).
- Tim, enrichment, dan tanda perlu ditinjau ditetapkan pada [Decision 2.4](./2.4-ownership.md).
- Event riwayat ditetapkan pada [Decision 2.5](./2.5-versioning.md).
- Field log `error_code` ditetapkan pada [Decision 1.7](../1-error-definition-framework/1.7-logging-dan-context.md).

## Konsekuensi

- Registry menyimpan riwayat publish yang ditolak selain catalog version.
- Kelengkapan data registry menjadi pekerjaan yang terlihat dan dapat ditugaskan ke tim.
- Frekuensi error tetap harus dilihat di sistem monitoring.
- Registry memerlukan keanggotaan tim untuk menentukan tampilan default pengguna.
