# 2.9 Integrasi dengan Sistem Lain

[← Kembali ke 2. Central Error Registry](./README.md)

> **TL;DR:** sistem lain seperti helpdesk, monitoring, atau chat tim bisa membaca registry dan diberi tahu ketika ada perubahan, tanpa registry harus dibuat khusus untuk setiap produk.

## Tujuan

Menetapkan cara sistem lain memakai data registry dan menerima pemberitahuan perubahan.

## Keputusan

### Bentuk Integrasi

Registry menyediakan tiga bentuk integrasi umum:

- link halaman error code yang stabil;
- read API [Decision 2.6](./2.6-pencarian.md) dan export [Decision 2.7](./2.7-sinkronisasi-lintas-aplikasi.md);
- webhook keluar untuk perubahan.

Registry tidak menyediakan connector khusus untuk produk helpdesk, monitoring, atau chat tertentu.

### Link Stabil

Setiap error code memiliki halaman dengan URL tetap:

```text
{registry-url}/errors/{code}
```

URL tersebut tetap berlaku walaupun kode sudah dihapus. Sistem monitoring dan helpdesk dapat membentuk link ini dari field `error_code` pada log [Decision 1.7](../1-error-definition-framework/1.7-logging-dan-context.md) atau dari kode yang dilaporkan pengguna.

### Webhook

Registry dapat mengirim webhook ke URL yang didaftarkan. Setiap webhook memilih event yang ingin diterima:

| Event | Kondisi |
|-------|---------|
| `catalog.published` | Catalog version baru diterima. |
| `catalog.rejected` | Publish ditolak. |
| `error.added` | Error code baru muncul. |
| `error.changed` | Field runtime error code berubah. |
| `error.removed` | Error code dihapus. |
| `error.restored` | Error code yang dihapus muncul kembali. |
| `error.review_required` | Enrichment ditandai perlu ditinjau. |

Payload menggunakan JSON:

```json
{
  "event": "error.changed",
  "occurredAt": "2026-10-13T10:30:00Z",
  "application": "surat-masuk",
  "revision": "a1b2c3d4e5f6",
  "code": "SM-WF-001",
  "changes": {
    "severity": { "before": "medium", "after": "high" }
  }
}
```

Field `code` dan `changes` hanya ada pada event `error.*`. Event `catalog.rejected` membawa `findings` sesuai [Decision 2.2](./2.2-validasi-schema.md).

Setiap request webhook ditandatangani dengan HMAC SHA-256 menggunakan secret per webhook, dikirim pada header `X-EDF-Signature`.

Registry mengulang pengiriman yang gagal beberapa kali dengan jeda yang makin panjang. Pengiriman yang tetap gagal dicatat dan dapat dilihat di registry.

### Arah Data

Integrasi hanya membaca data registry atau menerima pemberitahuan. Sistem lain tidak dapat mengubah catalog melalui integrasi. Perubahan enrichment oleh sistem lain tidak disediakan.

## Alasan

Bentuk integrasi umum dipilih karena produk helpdesk, monitoring, dan chat yang dipakai berbeda-beda dan dapat berganti. Link, API, dan webhook dapat dipakai oleh hampir semua produk tanpa registry mengikuti perubahan masing-masing.

Link stabil menjadi integrasi paling sederhana: monitoring yang sudah mencatat `error_code` cukup membentuk URL tanpa memanggil API.

Webhook dipilih agar sistem lain tidak perlu bertanya berulang kali apakah ada perubahan. Event dibuat per error code agar penerima dapat bereaksi pada kode atau aplikasi tertentu saja.

Tanda tangan HMAC memungkinkan penerima memastikan webhook benar berasal dari registry tanpa membuka akses tambahan.

Integrasi dibatasi pada membaca agar catalog tetap hanya berubah melalui publish dari aplikasi dan enrichment tetap melalui tim yang bertanggung jawab di registry.

✅ **Contoh:** Monitoring menampilkan lonjakan log dengan `error_code` `SM-WF-001` → dashboard monitoring menautkan ke `{registry-url}/errors/SM-WF-001`, karena link dapat dibentuk langsung dari field log.

❌ **Bukan contoh:** Meminta registry menyediakan plugin khusus untuk satu produk helpdesk → tidak disediakan, karena produk tersebut dapat memakai read API dan webhook yang sama.

## Keputusan Terkait

- Field `error_code` pada log ditetapkan pada [Decision 1.7](../1-error-definition-framework/1.7-logging-dan-context.md).
- Finding penolakan ditetapkan pada [Decision 2.2](./2.2-validasi-schema.md).
- Tanda perlu ditinjau ditetapkan pada [Decision 2.4](./2.4-ownership.md).
- Event riwayat ditetapkan pada [Decision 2.5](./2.5-versioning.md).
- Read API dan token baca ditetapkan pada [Decision 2.6](./2.6-pencarian.md).
- Export gabungan ditetapkan pada [Decision 2.7](./2.7-sinkronisasi-lintas-aplikasi.md).

## Konsekuensi

- Integrasi dengan produk tertentu dibuat di sisi produk tersebut atau melalui tool otomasi, bukan di registry.
- URL halaman error code menjadi kontrak yang tidak boleh berubah.
- Payload webhook menjadi kontrak publik yang perubahannya harus kompatibel.
- Registry harus mengelola pendaftaran webhook, secret, dan riwayat pengiriman.
