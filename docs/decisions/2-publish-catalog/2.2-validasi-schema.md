# 2.2 Validasi Schema

[← Kembali ke 2. Publish Catalog](./README.md)

> **TL;DR:** package menyertakan aturan resmi bentuk file catalog, sehingga sistem mana pun yang menerima catalog dapat memeriksanya dengan aturan yang sama seperti di aplikasi.

## Tujuan

Menetapkan kontrak bentuk kiriman publish yang dapat dipakai penerima untuk memvalidasi catalog, dan bagaimana kontrak tersebut dijaga tetap sama dengan aplikasi.

## Keputusan

### Sumber Aturan

Aturan struktur kiriman ditetapkan dalam JSON Schema yang disertakan package:

- `resources/schemas/publish-request.v1.json` untuk envelope [Decision 2.1](./2.1-publish-catalog-dari-aplikasi.md);
- `resources/schemas/error-catalog.v1.json` untuk catalog `schemaVersion: 1` pada [Decision 1.11](../1-error-definition-framework/1.11-generator-error-catalog-json.md).

Setiap `schemaVersion` baru mendapat file schema baru tanpa mengubah file versi sebelumnya.

### Yang Diperiksa

Envelope:

- `application` sesuai format slug Decision 2.1;
- `revision` berupa string tidak kosong dengan panjang maksimal 64 karakter;
- `catalog` berupa object.

Catalog:

- `schemaVersion` bernilai versi yang sesuai dengan file schema;
- `errors` berupa array;
- setiap error memiliki seluruh field runtime dengan tipe yang benar;
- `code` mengikuti format `^[A-Z0-9]+(?:-[A-Z0-9]+)+-\d{3,}$`;
- `message` tidak kosong;
- `category` dan `severity` merupakan backing value enum yang dikenal;
- `httpStatus` berada pada rentang `400–599`;
- `retryable` berupa boolean.

Keunikan `code` dalam satu catalog tidak dapat dinyatakan dengan JSON Schema dan tetap dijamin oleh EDF linter pada [Decision 1.8](../1-error-definition-framework/1.8-validator-dan-linter.md).

Schema mengizinkan field tambahan. Penerima disarankan mengabaikan field yang tidak dikenal.

### Peran Package

Package tidak memvalidasi kiriman saat publish karena catalog dibangun dari definisi yang sudah lolos linter. Test package memastikan output generator dan envelope publish selalu valid terhadap schema yang disertakan.

## Alasan

JSON Schema dipilih karena merupakan standar yang dapat dibaca dalam bahasa apa pun. Penerima catalog tidak harus aplikasi PHP.

Menyertakan schema di package membuat aturan penerima dan aplikasi berasal dari satu sumber, sehingga catalog yang lolos linter tidak ditolak karena perbedaan aturan.

Field tambahan diizinkan agar package versi baru yang menambahkan field secara non-breaking tetap dapat dibaca penerima lama. Perubahan yang breaking tetap ditandai dengan `schemaVersion` baru sesuai Decision 1.11.

Validasi saat publish tidak dilakukan karena hanya mengulang pemeriksaan linter. Test package sudah menangkap ketidaksesuaian antara generator dan schema sebelum rilis.

✅ **Contoh:** Package versi baru menambahkan field opsional `docsUrl` pada setiap error tanpa mengubah `schemaVersion` → penerima lama tetap menerima catalog dan mengabaikan field tersebut.

❌ **Bukan contoh:** Package mengubah `httpStatus` dari integer menjadi string → ini breaking change yang wajib menaikkan `schemaVersion` dan menambah file schema baru.

## Keputusan Terkait

- Envelope publish ditetapkan pada [Decision 2.1](./2.1-publish-catalog-dari-aplikasi.md).
- Bentuk catalog ditetapkan pada [Decision 1.11](../1-error-definition-framework/1.11-generator-error-catalog-json.md).
- Rule Error Definition aplikasi ditetapkan pada [Decision 1.8](../1-error-definition-framework/1.8-validator-dan-linter.md).

## Konsekuensi

- Package wajib menyertakan dan menjaga file JSON Schema untuk setiap `schemaVersion`.
- Perubahan aturan format error code harus dilakukan bersamaan di linter dan JSON Schema.
- Penerima yang ingin memeriksa keunikan error code harus melakukannya sendiri di luar JSON Schema.
- Penerima dapat mendukung beberapa `schemaVersion` sekaligus selama masa transisi.
